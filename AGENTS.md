# Работа с Норой

Прочитайте README.md и docs/ перед изменениями.

## Передача контекста (AI_HANDOFF)

- В начале новой сессии сначала читать `AGENTS.md`, затем `docs/AI_HANDOFF.md`.
- Перед началом работы сверять записанное состояние с фактическим `git status`
  и текущей веткой (`git branch --show-current`); при расхождении доверять
  фактическому состоянию репозитория и обновить AI_HANDOFF.md.
- После завершения значимой задачи обновлять `docs/AI_HANDOFF.md`.
- Перед завершением сессии фиксировать в нём: выполненное, оставшиеся задачи,
  важные решения.
- Не записывать туда огромные логи, полный код и повторяющуюся информацию;
  поддерживать документ компактным (~до 150 строк).
- Не делать отдельный коммит только ради обновления AI_HANDOFF.md без явного
  разрешения пользователя.

- Разрешены изучение кода, локальные ветки, изменения, тесты и подготовка обновлений.
- С 01.11.2026 по актуальному указанию владельца прежнее постоянное разрешение
  на публикацию отменено: не менять production-ветку и не выполнять commit,
  push, merge в production или deploy без явного разрешения на эти действия.
- Railway следит за cursor/nora-2-update-d133. Для разработки создавать
  отдельную ветку chatgpt/<название-задачи> от актуальной origin/cursor/nora-2-update-d133.
  Сначала проверить git status, выполнить git fetch origin и сверить базу с GitHub.
  Не переключать чужие ветки и не переносить незавершённые изменения без разбора.
  Не настраивать feature-ветку на отслеживание production-ветки для push.
- main отстаёт от production; проверяйте базовый SHA перед исправлением.
- Не запускайте main с рабочим BOT_TOKEN: startup меняет Telegram/SQLite,
  может публиковать Telegraph и объявления. Второй poller недопустим.
- Секреты не записывать в Git, аргументы команд, отчёты или stdout.
- Не тестировать на production SQLite. Использовать tmp_path и fake/mocked Bot.
- Проверки Windows: .venv/Scripts/python.exe tools/check_local.py и
  .venv/Scripts/python.exe -m pip check; Linux/macOS: .venv/bin/python.
- В документационном изменении не править постороннюю бизнес-логику.
- GitHub connector имеет Write; feature-ветки и PR доступны.
- Production DB и значения переменных не исследованы. Описание схемы по коду
  не является проверкой содержимого и целостности рабочей базы.

## Карта проекта (фактическая структура)

Один asyncio-процесс (community_bot/main.py) совмещает Telegram long polling
(aiohttp/aiogram) и Mini App HTTP-сервер (aiohttp). Данные — общая SQLite.

- `community_bot/main.py` — точка входа: запуск poller + HTTP + фоновые задачи.
- `community_bot/config.py` — чтение настроек из окружения (см. `.env.example`).
- `community_bot/database.py` — схема и все операции SQLite (общая с ботом).
- `community_bot/miniapp.py` — HTTP-сервер Mini App: маршруты `/api/*`, раздача
  статики из `community_bot/web/`, авторизация по Telegram initData (tma).
  Есть `/healthz`. Порт из `PORT` (по умолчанию 8080).
- `community_bot/routers/` — обработчики Telegram (private, group, games,
  pets, wallet, admin, shop_admin и др.).
- `community_bot/web/` — frontend Mini App (без сборки, файлы отдаются как есть):
  `index.html`, `style.css`, `app.js` (роутинг/рендер/press-feedback),
  `intro.js` (заставка), `home.js`, `shop.js`, `cabinet.js`, `admin.js`,
  `interactive.js`, `people.js`, `community.js`, `avatars.js`, `events.js`.
- API Mini App: `miniapp.py` + `*_api.py` (shop_api, events_api, cabinet_api,
  community_api, friends_api, mafia_api, rocket_api), `admin_web.py`,
  `social_profiles.py`, `seasonal.py`.
- Бизнес-логика: `economy.py`, `cookie_logic.py`, `reputation.py`,
  `event_manager.py`, `contest.py`, `pets_talk.py`/`expedition.py`, `notify.py`,
  `posting.py`, `morning.py`, `telegraph.py`, `stickers.py`.
- `assets/` — шрифты (fonts/Monocraft.ttf), заставка (branding), обложки,
  стикеры, иллюстрации. Отдаются через `/fonts/`, `/intro/`, `/home-art/`,
  `/art/` и т.д.
- `tests/` — pytest, изолированная SQLite + fake/mocked Bot.
- `tools/check_local.py` — Ruff + pytest с блокировкой сети Python.
- Docker: `Dockerfile`, `docker-entrypoint.sh`, `compose.yml`.
- Деплой: Railway автоматически разворачивает ветку `cursor/nora-2-update-d133`;
  SQLite-том смонтирован в /app/data. Не пушить в эту ветку без разрешения
  на публикацию.

## Работа над задачами

- Одна сессия — одна конкретная задача. Новую независимую задачу начинать
  в отдельной сессии после сохранения контекста текущей; продолжение той же
  задачи использует её существующую feature-ветку.
- Перед изменениями изучай относящийся к задаче код, а не предполагай по именам.
- Меняй минимальное число файлов; не трогай постороннюю логику «заодно».
- Сохраняй существующий дизайн NORA (палитра `--bg/--panel/--line/--muted/--red`,
  шрифт Monocraft для заголовков, системный sans для текста) и работающую логику.
- Не создавай дублирующие функции и CSS-правила: `style.css` содержит
  поздние переопределения — сначала ищи существующий селектор/анимацию.
- После изменений выполняй доступные проверки (node --check для JS,
  tools/check_local.py для Python). Если проверка не выполнена — честно
  укажи причину (нет .venv, нет окружения и т.п.).
- Перед завершением проверить git diff, git diff --check и git status;
  обновить handoff и кратко сообщить: что сделано, результаты тестов,
  ограничения и оставшиеся задачи. Не исправлять посторонние сбои «заодно».

## Безопасность

- Не выводи и не передавай секреты, токены, initData и содержимое .env;
  не читай .env без необходимости.
- Не изменяй production-БД, миграции и переменные Railway без отдельного
  разрешения владельца. Перед согласованным изменением БД нужен backup.
- Не выполняй force push, rebase, перезапись истории и переключение чужих веток.
- Не используй личность автора предыдущего коммита (user.name/user.email)
  без подтверждения пользователя; спроси, если Git identity не настроена.
- Не запускай production-бота локально и не используй рабочий BOT_TOKEN:
  второй poller и startup-эффекты недопустимы.

## GitHub и Railway

- По умолчанию изменения остаются только в локальном рабочем дереве.
- Commit, push и deploy — только при явном запросе пользователя.
- Перед публикацией: проверь текущую ветку, git status/diff, что в коммит
  не попадают .env, базы, ключи и посторонние изменения.
- Коммить только проверенные файлы (git add по именам, не «всё»).
- После публикации проверяй доступность приложения (`/healthz`) и фактическое
  появление новой версии (например, отличимый маркер в раздаваемой статике).
- Не заявляй об успешном деплое без фактического подтверждения.
- Railway CLI и RAILWAY_TOKEN обычно недоступны — подтверждай через публичные
  эндпоинты или честно сообщай, что статус не проверен.

## Эффективность контекста

- Не перечитывай весь репозиторий для каждой задачи; используй карту выше
  и точечный поиск (grep/glob) по путям.
- Не выводи большие файлы целиком: читай смещениями/фрагментами, для CSS
  и однострочных файлов используй grep по шаблону.
- Избегай повторных одинаковых инструментальных вызовов.
- При приближении к пределу контекста составь краткое резюме: сделано,
  осталось, важные решения, незавершённые изменения (файлы, ветка, хеши).
- При приближении лимита контекста (ориентир ~70–80%): подготовить краткое резюме
  текущей задачи в `docs/AI_HANDOFF.md` (сделано, осталось, решения, файлы,
  ветка, хеши) и предложить пользователю продолжить в новой сессии.
  Указать точный следующий шаг и результаты проверок, чтобы следующая сессия
  могла продолжить без повторного исследования. Не полагаться только на историю чата.
- Не теряй состояние незавершённой работы между сообщениями.
